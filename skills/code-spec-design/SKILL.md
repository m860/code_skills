# 方案设计（先设计后实现）

本技能是 `code-spec-common` 的专用层。只负责一个需求从 `方案设计中` 到 `方案设计完成`。设计结束即停。用户之后明确要求实现时，才按文末「实现门禁」编码。发版、重新部署不在本技能内。

开始前先读 `../code-spec-common/SKILL.md`。术语、目录、状态、文档位置、CHANGELOG 和共同约束以它为准，下文不重复。

先读代码和已有文档，再写方案。架构共性（含成熟库优先）先读 `../code-architecture/SKILL.md`，下文只写方案流程，不重复那些原则。

## 硬性约束

- 新需求只写增量。活文档里因本需求过时的陈述，同步时改掉。无歧义就写短，不保留已废弃结论。
- 设计阶段只读业务源码和文档，不改业务源码。
- 未同时满足「用户明确要求实现」和「没有未确认问题」之前，不写业务代码、测试代码，不改 `docs/cases/`。
- **可行性优先**：需求引入**新的技术方案**或**新的业务流程/协作流程**时，先做可行性判断（技术、业务、依赖、合规/权限、与现有系统冲突等）。判定**不可行**，或现有代码/文档不足以支撑结论、只能靠臆测时：**立即提示用户并停下**；禁止用假设把方案「圆」下去，禁止继续做无效的展开分析与设计。
- 涉及功能级实现时：先评估仓库已有能力与成熟库是否可用，对照本需求写出选项，**用户选择后再写入 TECH 定案**；不擅自引入依赖或默认自研。库选型仍受上条可行性约束。
- 原型只在用户明确要求时写。
- 不自动发版，不自动重新部署。

## 流程

```
- [ ] 1. 读现状，定 {timestamp}-{title}
- [ ] 2. 若有新技术方案或新流程：先做可行性判断；不可行或只能臆测则提示用户并停下
- [ ] 3. 建需求目录，并在 STATUS.md 登记为方案设计中
- [ ] 4. 写 SPEC.md + TECH.md；按需 BRD 与原型；按需同步数据模型、架构和规划
- [ ] 5. 待确认问题逐条决策并回写，直到没有开放问题
- [ ] 6. 把该行改为方案设计完成，停下等用户
- [ ] 7. 仅当用户明确要求实现且没有未确认问题时，才编码
```

### 1. 读现状，定目录名

先读，再定稿：

- `docs/features/` 里与本次相关的旧需求（SPEC / TECH / BRD）以及 `docs/features/STATUS.md`
- 相关业务源码、配置、接口
- `docs/DB.md`、`docs/ARCHITECTURE.md`、`docs/PLANNED-FEATURES.md`
- `docs/CHANGELOG.md` 只用来知道当前产品版本

目录名按 `code-spec-common` 定为 `{timestamp}-{title}`。`timestamp` 用当前本地时间。

### 2. 可行性门禁

在展开 SPEC / TECH 正文之前执行。触发条件（任一即可）：

- 引入仓库尚未采用的技术、依赖、基础设施或集成方式
- 引入新的业务主路径、协作流程、组织/系统间交接，或明显改变现有流程

判断时只依据已读到的代码、文档、环境约束与用户已给出的事实；**不补故事、不默认「以后可以解决」**。

| 结论 | 动作 |
| --- | --- |
| 可行（有依据） | 简要记下依据，进入后续步骤；细节写入 TECH / SPEC |
| 不可行（有依据） | **立即**向用户说明：不可行点、依据、若有可替换方向可作建议；**停止**本需求的方案展开（不写完整 SPEC/TECH 定案，不把状态推到 `方案设计完成`） |
| 证据不足、只能假设 | 视为未过门禁：**立即**提示缺什么信息或卡在哪；**停止**；等用户补充或改需求，不带着假设继续设计 |

设计过程中才发现新方案/新流程不可行或只能臆测：同样立即停下提示，撤回或标注未定结论，不假装方案已成立。

用户确认改需求、换方案或接受已知限制后，从本门禁或第 1 步重走，再继续设计。

### 3. 建目录并登记状态

按 `code-spec-common` 建目录并登记。新行状态写 `方案设计中`。这一步只建目录、登记状态、写文档。

若第 2 步已判定不可行或证据不足：可不建目录；若目录已建，保持 `方案设计中` 或按用户指示处理，**不**改为 `方案设计完成`。

### 4. 写方案文档

变更类型写在 SPEC 或 TECH 正文开头，取值与 `code-spec-common` 的 CHANGELOG 前缀相同。

本阶段写哪些，以 `code-spec-common` 的文档位置为准：

- 必写：SPEC.md、TECH.md；STATUS.md 新建为 `方案设计中`，收尾改为 `方案设计完成`
- 按需：BRD.md；用户要求时的原型；有变化才同步 `docs/DB.md`、`docs/ARCHITECTURE.md`、`docs/PLANNED-FEATURES.md`
- 不写：`docs/CHANGELOG.md`、`docs/cases/`、业务代码

#### SPEC.md（必需）— 产品方案

纯 fix：背景写在开篇，不另写 BRD。有新业务能力或流程变化：背景细节放 BRD，SPEC 写可执行的产品行为。

```markdown
# SPEC — {一句话}

> 需求时间戳：`YYYYMMDDHHmmss`
> 变更类型：`feat` | `fix` | `docs` | `chore`
> 相对：`{timestamp}-{title}`（有则点名实际目录名；不改那份文档）

## 背景
现状是什么、为什么要改。每条现状能指回代码、接口或旧文档。

## 范围
### 做
### 不做

## 功能组织
功能落在哪个模块、角色能做什么、规则表。

## 交互流程
有界面就写页面与操作。没有界面写操作者改什么（配置、命令、数据）。

## 业务流程
主路径。必要时用缩进步骤，写清分支条件。

## 边界情况
空值、缺字段、权限、失败、与旧行为的差异。每条写结果，不写「视情况」。

## 待确认问题
没有则写「无」。有则只留尚未拍板的条目；拍板后删掉该条并把结论写进正文。
```

#### TECH.md（必需）— 技术方案

只写本需求的技术增量，不重抄全库架构和全量数据模型。

```markdown
# TECH — {与 SPEC 同一句话}

## 技术增量概述
改哪些模块、新增或调整哪些行为。有无数据变更。

## 现状（只读对照）
相关文件、入口（调用方式与标识）、数据、配置项。与代码不一致就停下来问。

## 依赖与库选型
本需求涉及的功能实现：已评估的仓库既有能力 / 成熟库 / 自研路径；对照本需求的覆盖与缺口；**用户已选方案**及简要理由。无需选型则写「无新依赖选型」。用户未拍板前，选项只放在「待确认问题」，不在此写成定案。

## 改动点
模块或文件、接口契约、配置、算法或伪逻辑。写到实现时不用再猜的程度。实现方式跟随仓库已有约定与已确认的库选型。

## 数据
有结构或字段变更：写增量（哪些数据、字段、约束、结构如何变化），并同步全量 `docs/DB.md`。
没有：写「无数据变更，不改 docs/DB.md」。
结构变更与内容变更分开写。内容变更不自动执行；做法跟随仓库已有约定，没有约定就只写意图。

## 配置
新增、改语义、或明确「不变」。空值与失败时的行为写进 SPEC 的边界，这里写键名与解析。

## 测试意图（实现阶段才落文件）
点名将更新的 `docs/cases/{MODULE}.md`（模块名全大写）以及要覆盖的行为。设计阶段不创建、不修改用例文档和测试代码。

## 非目标
本需求明确不动的范围，含不改旧需求文档。
```

架构以 `docs/ARCHITECTURE.md` 为准。本需求若改变架构级事实，在 TECH 写增量，并同步其中已过时的对应陈述。没有架构级变化则不改该文件。成熟库与自研的取舍原则以 `code-architecture` 为准。

#### BRD.md（按需）

有新业务能力或流程变化时写。纯 fix、纯技术调整、无流程变化：省略。

必写：背景、目的、干系人与场景、成功标准、非目标。场景写谁在什么情况下做什么，以及怎样算做成。

#### 原型（按需）

仅用户明确要求时，在同一需求目录放一份原型，表达 SPEC 里的交互，不代替 SPEC。形式跟随仓库已有原型；没有约定时，用一份不绑定具体页面技术的原型说明交互。

#### 同步规划

本需求明确不做、但以后仍要做的能力：追加到 `docs/PLANNED-FEATURES.md`。一条一个能力，一句或一段；能拆开就拆成多条；无序列表。不要写「已编码」「待做」这类状态词。该能力在后续需求落地后，从列表删除对应条目。本需求没有此类遗留则不改这个文件。

### 5. 待确认问题

写文档前在内部先列出全部开放问题（业务规则、数据来源、权限、失败行为、与旧需求冲突、**功能实现的库选型**）。**可行性未过门禁的项不是「待确认问题」里的普通条目**——按第 2 步立即提示并停下，不混进逐条拍板队列里继续写方案。

没有开放问题则进入第 6 步。

有库选型时：先按 `code-architecture` 完成「已有能力 → 成熟库 → 对照本需求」的分析，再作为待确认问题请用户选择；未确认前 TECH 的「依赖与库选型」不写定案。某选项若已判定不可行，不得当作默认可行选项写进定案。

有问题时，每次回复只处理一条，禁止并列多问。格式固定：

```
问题：…
说明：…
建议：…
请决策：…
```

库选型类问题在「说明」中写清各选项的覆盖范围、缺口、风险与接入成本；「请决策」列出可选路径（含自研或「库 + 少量自研」）。

用户拍板后：把结论写进 SPEC / TECH / BRD 的正文（库选型写入 TECH「依赖与库选型」），删掉该条开放问题，再发下一条。全部确认后才进入第 6 步。

用户在启动本技能的消息里已经拍板的点，写成结论，不要再问一遍。

### 6. 设计完成 → 停止

同时做到：

1. 可行性门禁已通过（无未解除的不可行/纯臆测项）。
2. 开放问题为零（SPEC 的「待确认问题」为「无」）。
3. 只把该需求在 `STATUS.md` 中的状态从 `方案设计中` 改为 `方案设计完成`。
4. 回复目录路径、状态、已写和已改的文件列表。
5. 停止。不编码，不发版，不问一串实现细节。用户要实现时会另说。

### 7. 实现门禁

只有下面两条同时成立才写代码：

1. 用户明确要求实现（「开始实现」「按方案做」「编码」等）。
2. 当前需求没有未确认问题，且无未解除的可行性阻断。有则回到第 2 或第 5 步，不写代码。

通过后：

- 编码前再核对：行为都在当前需求的 SPEC / TECH 里。缺了先补文档，再写代码。
- 先写实现计划。无相互依赖的工作包可以分开完成；仍属于当前需求目录，不新建时间戳。
- 按依赖分层：当前层做完再进下一层。
- 相同逻辑放一处复用，不复制到第二处。
- 测试按「测试约束」。用例文档是真源，不把用例写进 `docs/features/`。
- 版本、CHANGELOG、提交和发版遵守 `code-spec-common`。
- 编码和测试完成后，只把 `STATUS.md` 里该行改为 `已实现`，然后问用户要不要改为 `待部署`。用户没确认之前，停在 `已实现`。

## 测试约束

只在第 7 步实现时使用。

- 用例文档：`docs/cases/{MODULE}.md`，`{MODULE}` 全大写、按产品域稳定命名。一条用例写清对象、步骤、期望，并标明是逻辑或接口验证，还是界面流程验证。
- **界面流程验证用 Playwright MCP** 执行：以用例文档为步骤与期望真源，经 Playwright MCP 驱动浏览器操作与断言；不另起竞争 E2E 栈。
- **E2E 登录**：系统需要登录时，打开页面等待用户进行登录操作；禁止 mock 和注入的方式实现（如注入 token / cookie / localStorage、改存储冒充会话、路由绕过登录页等）。业务数据仍按下文「E2E 数据」处理，与登录方式无关。
- **E2E 数据**：默认一律用 mock 数据。用户对部分数据有明确提供时，该部分改用用户提供的数据；未提供的部分仍用 mock。
- **E2E 与第三方系统**：流程若依赖第三方/外部系统，且用户未明确说明如何测（真实联调、替身、账号、环境等），**默认跳过**该部分；测完后必须告知用户：哪些流程/功能因依赖何第三方、因未约定测法而未测。用户已明确测法的，按约定执行，不默认跳过。
- 逻辑/接口等其余测试的目录、命名和运行方式跟随仓库已有约定。仓库没有测试约定时先问，再按确认结果写。
- 新需求按影响到的模块增量更新对应用例文件。
- 依赖外部系统的用例在用例文档标明可跳过及依赖哪个外部系统；E2E 执行时另按上文「E2E 与第三方系统」处理。

## 完成时输出

设计结束（第 6 步）时只输出：

1. 目录路径（`docs/features/{timestamp}-{title}/`）和 `STATUS.md` 中的状态（此时为 `方案设计完成`）
2. 已写、已改的文档列表

若卡在第 2 步可行性门禁：只输出不可行或证据不足的说明与待用户决定的点，不输出「设计完成」总结。

若还在第 5 步，不要输出完成总结，只发当前这一条待确认问题。

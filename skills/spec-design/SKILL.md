# 方案设计（先设计后实现）

本技能只负责一个需求从 `方案设计中` 到 `方案设计完成`。设计结束即停。用户之后明确要求实现时，才按文末「实现门禁」编码。发版、重新部署不在本技能内。

在产品仓库中执行（含 `docs/` 的那个仓库）。先读代码和已有文档，再写方案。

## 术语

- **版本** = SemVer（如 `1.2.0`），与需求目录时间戳无关。
- **当前产品版本** = `docs/CHANGELOG.md` 最上一条 `## X.Y.Z`。没有任何 `## X.Y.Z` 区段 = 尚未发版。不以源码里的版本号反推。
- **需求** = `docs/features/{timestamp}-{title}/`。一个目录一个需求，里面是产品方案和技术方案。目录名创建后不再改。
- **需求状态**只写在 `docs/features/STATUS.md`，不写进目录名。流转只改该文件里这一行：

  `方案设计中`（新建默认）→ `方案设计完成`（本技能收尾）→ `已实现`（编码和测试完成）→ `待部署`（用户明确纳入本次上线）→ `已部署`（发版成功）

- **源码版本号**：仓库源码中的版本字段，不随设计、实现、发版、重新部署改动。
- **Release 版本**：只写入发布产物。设计与实现阶段都不发布。
- **发版**（用户说「部署」或「deploy」）：圈定 `STATUS.md` 里状态为 `待部署` 的全部需求 → 一个新 SemVer → 发布并上线。本技能不执行。
- **重新部署**：用当前顶版再发布上线；不升版、不改需求状态。本技能不执行。

## 硬性约束

- 业务、数据、接口、流程必须以读到的代码或已有文档为依据。读不到、对不上、有多种解释：先问，禁止补故事。
- 新需求只写增量。不改旧需求目录里的文档，也不重命名任何需求目录。状态只改 `docs/features/STATUS.md` 里当前这一行。
- 设计阶段可以读业务源码和文档，禁止改业务源码。
- 未同时满足「用户明确要求实现」和「没有未确认问题」之前，不写业务代码、不写测试代码、不改 `docs/cases/`。
- 设计阶段和实现阶段都不写、不改 `docs/CHANGELOG.md`（含 `LAST_SHIPPED`），都不改源码中的版本号。
- `DEMO.html` 只在用户明确要求原型时写。
- 禁止自动提交。禁止自动发版、自动重新部署。
- 无歧义就写短。不写重复句、不保留已废弃结论。活文档（`docs/DB.md`、`docs/ARCHITECTURE.md`、`docs/PLANNED-FEATURES.md`）里发现本需求造成的过时陈述，在同步时改掉。旧需求目录里的过时内容不回改，只在本需求写增量。

## 流程

```
- [ ] 1. 读现状，定 {timestamp}-{title}
- [ ] 2. 建 docs/features/{timestamp}-{title}/，并在 STATUS.md 登记为方案设计中
- [ ] 3. 写 SPEC.md + TECH.md；按需 BRD.md / DEMO.html；按需同步 DB.md、PLANNED-FEATURES.md
- [ ] 4. 待确认问题逐条决策并回写，直到没有开放问题
- [ ] 5. 把 STATUS.md 中该行改为方案设计完成，停下等用户
- [ ] 6. 仅当用户明确要求实现且没有未确认问题时，才编码
```

### 1. 读现状，定目录名

先读，再定稿：

- `docs/features/` 里与本次相关的旧需求（SPEC / TECH / BRD）以及 `docs/features/STATUS.md`
- 相关业务源码、配置、接口
- `docs/DB.md`、`docs/ARCHITECTURE.md`、`docs/PLANNED-FEATURES.md`
- `docs/CHANGELOG.md` 只用来知道当前产品版本，不要改它

目录名 = `{timestamp}-{title}`，创建后不再改。

- `timestamp` = 当前本地时间 `YYYYMMDDHHmmss`（14 位）。
- `title` = 短标题，用来让目录名可读。中文或英文，词与词只用 `-` 连接。不含空格，不含状态，不含 `/` 和标点（`：` `「」` `,` `.` 等）。
- 例：`20260101140530-关键词匹配应用清单`。
- 先对照已有目录和 `STATUS.md`。重名，或短标题拿不准时，先问用户，不要擅自另起一个时间戳或改已有目录名。引用旧需求时用它实际的文件夹名。

### 2. 建目录并登记状态

```
docs/features/20260101140530-关键词匹配应用清单/
```

同时写 `docs/features/STATUS.md`。文件不存在就新建。新行插在表头下第一行（新的在上）：

```markdown
# 需求状态

目录名创建后不变。状态只改本表对应行。

| 目录 | 状态 |
| --- | --- |
| 20260101140530-关键词匹配应用清单 | 方案设计中 |
```

- `目录` 列等于文件夹名，不带 `docs/features/`。
- 一行一个需求。状态只允许：`方案设计中`、`方案设计完成`、`已实现`、`待部署`、`已部署`。
- 不删行，不改其他需求的状态，不把状态写进目录名或另建第二份清单。

这一步只建目录、登记状态、写文档。

### 3. 写方案文档

变更类型（`feat` / `fix` / `docs` / `chore` 等）写在 SPEC 或 TECH 正文开头，不另建清单。发版时才把本次上线的变更归进 CHANGELOG。设计阶段不写。

#### SPEC.md（必需）— 产品方案

纯 fix：背景写在开篇，不另写 BRD。有新业务能力或流程变化：背景细节放 BRD，SPEC 写可执行的产品行为。

```markdown
# SPEC — {一句话}

> 需求时间戳：`YYYYMMDDHHmmss`
> 变更类型：`feat` | `fix` | `docs` | `chore`
> 相对：`{timestamp}-{title}`（有则点名实际目录名；不改那份文档）

## 背景
现状是什么、为什么要改。每条现状能指回代码、接口或旧文档。

## 范围
### 做
### 不做

## 功能组织
功能落在哪个模块、角色能做什么、规则表。

## 交互流程
有界面就写页面与操作。没有界面写「无 UI」以及操作者改什么（配置、命令、数据）。

## 业务流程
主路径。必要时用缩进步骤，写清分支条件。

## 边界情况
空值、缺字段、权限、失败、与旧行为的差异。每条写结果，不写「视情况」。

## 待确认问题
没有则写「无」。有则只留尚未拍板的条目；拍板后删掉该条并把结论写进正文。
```

#### TECH.md（必需）— 技术方案

只写本需求的技术增量，不重抄全库架构和全量表结构。

```markdown
# TECH — {与 SPEC 同一句话}

## 技术增量概述
改哪些模块、新增或调整哪些行为。有无数据变更。点明不改 CHANGELOG、不改源码中的版本号。

## 现状（只读对照）
相关文件、入口（调用方式与标识）、数据、配置项。与代码不一致就停下来问。

## 改动点
模块或文件、接口契约、配置、算法或伪逻辑。写到实现时不用再猜的程度。

## 数据
有结构或字段变更：写增量（数据集、字段、约束、迁移意图），并同步全量 `docs/DB.md`。
没有：写「无数据变更，不改 docs/DB.md」。
结构变更与数据内容变更分开写。数据内容变更不随进程启动自动执行。存放位置跟随仓库已有约定；没有约定就只写意图，不另造一套目录。

## 配置
新增、改语义、或明确「不变」。空值与失败时的行为写进 SPEC 的边界，这里写键名与解析。

## 测试意图（实现阶段才落文件）
点名将更新的 `docs/cases/{MODULE}.md`（模块名全大写）以及要覆盖的行为。设计阶段不创建、不修改用例文档和测试代码。

## 非目标
本需求明确不动的范围，含不改旧需求文档。
```

架构以 `docs/ARCHITECTURE.md` 为准。本需求若改变架构级事实，在 TECH 写增量，并同步 `docs/ARCHITECTURE.md` 里已过时的对应陈述。没有架构级变化则不改该文件。

#### BRD.md（按需）

有新业务能力或流程变化时写。纯 fix、纯技术调整、无流程变化：省略。

必写：背景、目的、干系人与场景、成功标准、非目标。场景写谁在什么情况下做什么，以及怎样算做成。

#### DEMO.html（按需）

仅用户明确要求原型时生成，放在同一需求目录。用静态页表达 SPEC 里的交互，不代替 SPEC。

#### 同步规划

本需求明确不做、但以后仍要做的能力：追加到 `docs/PLANNED-FEATURES.md`。一条一个能力，一句或一段；能拆开就拆成多条；无序列表。不要写「已编码」「待做」这类状态词。该能力在后续需求落地后，从列表删除对应条目。本需求没有此类遗留则不改这个文件。

#### 全库文档一览

| 文件 | 设计阶段 |
| --- | --- |
| `docs/features/{timestamp}-{title}/SPEC.md` | 必写 |
| 同目录 `TECH.md` | 必写 |
| 同目录 `BRD.md` | 新业务能力或流程变化才写 |
| 同目录 `DEMO.html` | 用户明确要求才写 |
| `docs/features/STATUS.md` | 必登记；新建为 `方案设计中`，收尾改为 `方案设计完成` |
| `docs/DB.md` | 有数据库变更才改；全量，唯一 |
| `docs/ARCHITECTURE.md` | 架构级事实变化才改 |
| `docs/PLANNED-FEATURES.md` | 有明确留到以后的能力才追加 |
| `docs/CHANGELOG.md` | 不写 |
| `docs/cases/` | 不写（实现阶段再写） |

`docs/CHANGELOG.md` 长这样，用来识别，设计时不要起草也不要预写条目：

```markdown
# Changelog

LAST_SHIPPED: YYYYMMDDHHmmss

## X.Y.Z (YYYY-MM-DD)

- feat: …
- fix: …
```

`LAST_SHIPPED` 是最近一次实际上线时刻。版本区段新版本在上，日期是该版本首次发版日。条目用 `feat:` / `fix:` / `docs:` / `chore:` 前缀，纯文本，不放仓库路径。这些只在发版成功时写入，不是本技能的产出。

### 4. 待确认问题

写文档前在内部先列出全部开放问题（业务规则、数据来源、权限、失败行为、与旧需求冲突）。没有则进入第 5 步。

有问题时，每次回复只处理一条，禁止并列多问。格式固定：

```
问题：…
说明：…
建议：…
请决策：…
```

用户拍板后：把结论写进 SPEC / TECH / BRD 的正文，删掉该条开放问题，再发下一条。全部确认后才进入第 5 步。

用户在启动本技能的消息里已经拍板的点，写成结论，不要再问一遍。

### 5. 设计完成 → 停止

同时做到：

1. 开放问题为零（SPEC 的「待确认问题」为「无」）。
2. 只把 `docs/features/STATUS.md` 里该需求的状态从 `方案设计中` 改为 `方案设计完成`。不重命名目录。
3. 回复目录路径、状态、已写和已改的文件列表。
4. 停止。不编码，不提交，不发版，不问一串实现细节。用户要实现时会另说。

### 6. 实现门禁

只有下面两条同时成立才写代码：

1. 用户明确要求实现（「开始实现」「按方案做」「编码」等）。
2. 当前需求没有未确认问题。有则回到第 4 步，不写代码。

通过后：

- 编码前再核对：行为都在当前需求的 SPEC / TECH 里。缺了先补文档，再写代码。
- 先写实现计划。无相互依赖的工作包可以交给独立 sub agent；仍属于当前需求目录，不新建时间戳。
- 按依赖分层：当前层做完再进下一层。
- 相同逻辑放一处复用，不复制到第二处。
- 测试按「测试约束」。用例文档是真源，不把用例写进 `docs/features/`。
- 仍不改源码中的版本号，仍不写 CHANGELOG，仍不发版、不重新部署。
- 编码和测试完成后，只把 `STATUS.md` 里该行改为 `已实现`，然后问用户要不要改为 `待部署`。用户没确认之前，停在 `已实现`。不重命名目录。

## 测试约束

只在第 6 步实现时使用。

- 用例文档：`docs/cases/{MODULE}.md`，`{MODULE}` 全大写、按产品域稳定命名。一条用例写清对象、步骤、期望，并标明是逻辑或接口验证，还是界面流程验证。
- 测试代码跟随仓库已有的目录、命名和运行方式。本技能不规定语言、框架、目录或命令。仓库没有测试约定时先问，再按确认结果写。
- 新需求按影响到的模块增量更新对应用例文件。
- 依赖外部系统才能跑完的用例，在用例文档标明可跳过，并写清依赖哪个外部系统。未标记的不得擅自跳过。

## 完成时输出

设计结束（第 5 步）时只输出：

1. 目录路径（`docs/features/{timestamp}-{title}/`）和 `STATUS.md` 中的状态（此时为 `方案设计完成`）
2. 已写、已改的文档列表

若还在第 4 步，不要输出完成总结，只发当前这一条待确认问题。
